Isolation Technologies

Introduction

Sandbox isolation has become critical for agentic AI systems that generate and execute untrusted code dynamically. Unlike traditional applications with static code paths, AI agents create executables on-the-fly based on natural language instructions, making robust isolation essential for security.

The word "isolation" is used loosely across different technologies. A Docker container is "isolated." A microVM is "isolated." A WebAssembly module is "isolated." But these represent fundamentally different security boundaries with distinct failure modes and attack surfaces.

Core Insight: Every isolation technique answers the same question: How do we reduce or eliminate untrusted code's access to the kernel attack surface? The approaches differ in where they draw the boundary and what they consider shared versus dedicated state.

This analysis is based on research by Shayon Mukherjee, adapted for agentic security contexts.

The Attack Surface Model

When any code runs on Linux, it interacts with hardware through the kernel via system calls. The Linux kernel exposes roughly 340 syscalls and contains tens of millions of lines of C code. Every syscall represents a potential entry point into this massive attack surface.

Untrusted Code ─( Syscall )─→ Host Kernel ─( Hardware API )─→ Hardware [ 40M LOC C ]

This creates a fundamental challenge for agentic systems: AI-generated code has access to the same kernel interface as any other process, with all the associated vulnerabilities and attack vectors.

Shared State vs. Dedicated State

A key concept in isolation design is the distinction between shared state and dedicated state:

  • Shared State: Standard containers share the host kernel and its internal data structures (TCP/IP stack, VFS caches, memory allocators)
  • Dedicated State: Stronger isolation models push complex state into the sandbox, exposing only simple interfaces to the host

When state is shared, a vulnerability in kernel packet parsing affects every container on the host. Stronger isolation models minimize this shared attack surface by dedicating resources to individual workloads.

The Isolation Spectrum

Understanding isolation requires recognizing that different techniques provide qualitatively different boundaries, not just stronger versions of the same protection. Each step represents a fundamentally different security model.

Isolation Strength → Attack Surface ↓ Namespaces Seccomp gVisor MicroVM WASM │ │ │ │ │ │ visibility │ syscall │ separate │ hardware │ no kernel │ walls only │ filter on │ kernel in │ boundary │ access at │ │ same │ user-space│ via KVM │ all │ │ kernel │ │ │ ▼ ▼ ▼ ▼ ▼ Fast Fast Moderate Slower Fastest Weakest Weak Strong Strongest Strong* (*limited scope)

The progression from left to right represents not just increasing security, but fundamentally different approaches to the isolation problem. Each has specific use cases where it provides the optimal balance of security, compatibility, and performance.

Namespaces: Visibility Walls

Linux namespaces wrap global system resources so processes appear to have their own isolated instance. There are eight types of namespaces, each isolating specific resources:

Namespace Isolates What Process Sees
PID Process IDs Own process tree, starts at PID 1
Mount Filesystem mount points Own mount table, different root
Network Network interfaces, routing Own interfaces, IP addresses, ports
User UID/GID mapping Can be root inside, nobody outside
UTS Hostname Own hostname
IPC SysV IPC, POSIX message queues Own shared memory, semaphores
Cgroup Cgroup root directory Own cgroup hierarchy
Time System clocks Own system uptime, clock offsets
Critical Limitation: Namespaces are visibility walls, not security boundaries. They prevent processes from seeing resources outside their namespace but do not prevent kernel exploitation. A vulnerability in the kernel affects all containers regardless of namespace isolation.

Real-World Container Escapes

Recent container escape vulnerabilities demonstrate the limitations of namespace-based isolation:

  • CVE-2024-21626 (runc): File descriptor leak allowed container access to host filesystem despite intact mount namespace
  • CVE-2025-31133, CVE-2025-52565, CVE-2025-52881: Three runc CVEs in 2025 showing mount race conditions enabling host filesystem writes

These examples show that namespace integrity doesn't guarantee isolation when the underlying container runtime or kernel has vulnerabilities.

Cgroups: Resource Accounting

Control groups (cgroups) limit and account for resource usage: CPU, memory, disk I/O, and process count. They prevent containers from consuming all available system resources, providing stability but not security.

Important Distinction: Cgroups prevent denial-of-service attacks but are not a security boundary. They control resource consumption, not kernel access. A process constrained by cgroups still makes syscalls to the same kernel with the same attack surface.

For agentic AI systems that may spawn compute-intensive tasks (model inference, data processing, compilation), cgroups provide essential resource governance but should not be considered a security control.

Seccomp-BPF: Syscall Filtering

Seccomp-BPF allows attachment of Berkeley Packet Filter programs to control which syscalls a process can make. Docker applies a default seccomp profile that blocks 40-50 dangerous syscalls including process tracing, filesystem manipulation, and kernel module loading.

Without Seccomp: Untrusted Code ─( ~340 syscalls )─→ Host Kernel With Seccomp: Untrusted Code ─( ~300 syscalls )─→ Host Kernel

Seccomp meaningfully reduces the attack surface by preventing access to high-risk syscalls. However, allowed syscalls still enter the host kernel's code paths. If there's a vulnerability in write() implementation or the network stack, seccomp provides no protection.

Privileged Mode Considerations

Security Trade-off: Some isolation approaches require Docker's --privileged flag to get CAP_SYS_ADMIN for nested namespaces. This removes seccomp, capability restrictions, and device isolation. The net effect may be weaker than standard unprivileged containers.

For agentic systems requiring nested isolation, prefer granting specific capabilities rather than full privileged access, or use different isolation approaches that don't require host-level privileges.

gVisor: User-Space Kernels

gVisor represents a qualitative shift in isolation by interposing a separate kernel implementation (the Sentry) between untrusted code and the host. This fundamentally changes the attack surface rather than just filtering it.

Standard Container (Docker) ┌───────────────────────┐ │ Untrusted Code │ └──────────┬────────────┘ │ ~340 syscalls ▼ [ Seccomp Filter ] │ ~300 allowed syscalls ▼ ┌───────────────────────┐ │ Host Kernel (Ring 0) │ ◄── FULL ATTACK SURFACE └───────────────────────┘ gVisor ┌───────────────────────┐ │ Untrusted Code │ └──────────┬────────────┘ │ ~340 syscalls ▼ ┌───────────────────────┐ │ gVisor Sentry (Ring 3)│ ◄── USER-SPACE KERNEL └──────┬────────┬───────┘ │ │ 9P / LISAFS │ ▼ │ ┌───────────┐ │ │ Gofer │ ◄── FILE I/O PROXY │ └─────┬─────┘ │ │ ▼ ▼ ┌───────────────────────┐ │ Host Kernel (Ring 0) │ ◄── REDUCED ATTACK SURFACE └───────────────────────┘ (~70 host syscalls from Sentry)

gVisor Architecture

The Sentry intercepts syscalls and handles them in user-space, implementing ~200 Linux syscalls in Go. When it needs to interact with the host (file operations, network), it uses a highly restricted set of ~70 host syscalls. The failure mode changes significantly:

  1. Attacker must first compromise the Sentry process (Go implementation, memory-safe)
  2. Then escape from Sentry to host using only limited host syscalls

This is fundamentally different from filtering the same surface—it's a completely different surface with different implementations and attack vectors.

Key Advantage: If someone discovers a vulnerability in Linux kernel I/O handling, Docker containers are directly exposed. gVisor sandboxes are not, because the Sentry handles those syscalls internally without exposing them to the host kernel.

Defense in Depth on gVisor

For multi-job isolation within a single gVisor sandbox, layer additional controls:

gVisor Container (runsc) └─ Per-job PID + Mount Namespace └─ Seccomp BPF Filter └─ Privilege Drop └─ Network Egress Control └─ Ephemeral tmpfs └─ Capability-confined File Writes

Each layer catches different attack classes:

  • Namespace escape → reaches Sentry, not host kernel
  • Seccomp bypass → hits Sentry's syscall implementation (also sandboxed)
  • Privilege escalation → blocked by privilege drop
  • Persistent state leakage → prevented by ephemeral tmpfs with atomic cleanup

Performance Trade-offs

gVisor adds overhead through user-space syscall interception. I/O-heavy workloads feel this most. For agentic AI systems:

  • Short-lived code execution: Usually acceptable overhead
  • High-throughput I/O: May need different isolation approach
  • Model inference: CPU-bound workloads less affected

MicroVMs: Hardware Boundaries

MicroVMs use hardware virtualization to run each workload in its own virtual machine with dedicated kernel. This provides the strongest isolation boundary available through hardware enforcement.

MicroVM Architecture ┌───────────────────────┐ │ Untrusted Code │ └──────────┬────────────┘ │ Syscalls ▼ ┌───────────────────────┐ │ Guest Kernel (Ring 0) │ ◄── DEDICATED KERNEL └──────────┬────────────┘ │ VirtIO / MMIO ▼ ┌───────────────────────┐ │ KVM Hypervisor (Host) │ ◄── HARDWARE BOUNDARY └──────────┬────────────┘ │ Secure API ▼ ┌───────────────────────┐ │ VMM (User-Space) │ ◄── DEVICE EMULATION └───────────────────────┘

Security Properties

  • Hardware-enforced separation: Guest runs in separate virtual address space
  • Kernel bugs contained: Guest kernel vulnerabilities cannot access host memory
  • Minimal attack surface: Only hypervisor and VMM device emulation exposed
  • Escape requirements: Vulnerabilities in VMM or CPU virtualization features (rare and high-value)

VMM Design Approaches

Two main approaches to Virtual Machine Monitor design serve different use cases:

Minimal VMMs (Firecracker)

  • Built for thousands of tiny, short-lived functions
  • Minimal features: no hot-plugging, GPU passthrough, etc.
  • Smallest possible attack surface and memory footprint
  • Ideal for serverless and CI workloads

Feature-Rich VMMs (Cloud Hypervisor, QEMU)

  • Support for dynamic workloads
  • Hot-plugging memory and CPUs
  • GPU passthrough for AI workloads
  • More complex but more flexible

Performance Optimization: Snapshotting

Snapshotting captures running VM state (CPU registers, memory, devices) for rapid restoration. This enables warm pools where you:

  1. Boot VM once, install dependencies
  2. Snapshot the prepared state
  3. Restore clones in milliseconds

This technique achieves fast cold starts even with full VM isolation, making microVMs practical for latency-sensitive agentic applications.

Trade-off vs. gVisor: MicroVMs have higher per-instance overhead but provide stronger, hardware-enforced isolation. Choose based on threat model: microVMs for high-security scenarios, gVisor for better compatibility and lower overhead.

WebAssembly: No Kernel Access

WebAssembly takes a fundamentally different approach by providing no syscall interface at all. Code runs in a memory-safe virtual machine that can only interact with the host through explicitly imported functions.

WebAssembly (WASM) ┌───────────────────────┐ │ Untrusted Code │ └──────────┬────────────┘ │ Function Calls ▼ ┌───────────────────────┐ │ WASM Runtime (Host) │ ◄── MEMORY-SAFE VM └──────────┬────────────┘ │ Imported Host Functions ▼ ┌───────────────────────┐ │ Allowed Host APIs │ ◄── EXPLICIT CAPABILITIES └───────────────────────┘

Security Properties

  • No syscall attack surface: Code cannot make system calls directly
  • Memory safety: Linear memory bounds-checked, call stack inaccessible
  • Type safety: Control flow type-checked at runtime
  • Explicit capabilities: Only imported host functions available
  • Isolation by default: WASM modules cannot access filesystem, network, or other resources unless explicitly granted

Performance Characteristics

  • Fast cold starts: Near-instantaneous initialization
  • Minimal overhead: Low memory footprint
  • Portable: Same bytecode runs on any WASM runtime

Language Support Status

WASM language support has improved significantly since early 2025:

  • Python: wasm32-unknown-wasip1 is Tier 2 supported for CPython, with unofficial WASI builds available
  • JavaScript: QuickJS compiled to WASM works well for sandboxed execution
  • Scientific Computing: Pyodide ports CPython to WASM with NumPy, pandas, SciPy support
  • Server-side: Wasmer can run Python including native modules like gevent and SQLAlchemy
Agentic Application: WASM is excellent for controlled execution of agent-generated code where you control the toolchain. For arbitrary language support, containers or VMs remain necessary, but WASM provides unmatched security for supported use cases.

Agentic AI Security Implications

AI agents introduce unique security challenges that traditional sandboxing must address. The non-deterministic nature of AI-generated code execution requires careful consideration of isolation strategies.

Dynamic Code Generation Challenges

  • Runtime code creation: Traditional sandboxing assumes static code; agents create executables dynamically
  • Intent vs. implementation gap: Natural language instructions may be ambiguous, leading to unintended code execution
  • Tool access complexity: Agents need powerful capabilities (filesystem, network, APIs) that become attack vectors when compromised
  • Multi-agent coordination: Cascading failures when one compromised agent affects others in the network

Network Egress: The Other Half of Isolation

Compute isolation is only half the security story for agentic systems. Perfect sandbox isolation becomes meaningless if the agent can exfiltrate secrets over unrestricted network connections.

Critical Gap: An agent confined in a gVisor sandbox or Firecracker microVM can still exfiltrate every secret it can read over an outbound HTTP connection if network access is unrestricted.

Network Isolation Strategies

  1. No network access: For pure compute tasks that don't require external communication
  2. Stripped network namespace: Container with no external route
  3. Proxy-based allowlisting: Squid proxy with DNS blocking, domain-level allowlist
  4. Explicit capability grants: Agent must request permission for specific destinations
  5. Credential injection: Proxy handles authentication, agent never sees raw secrets

Local Developer Sandboxing

AI coding assistants represent a different threat model than server-side isolation. The concern isn't multi-tenancy but preventing agents from accessing sensitive local data.

Current Industry Approaches

  • Cursor: Uses Apple Seatbelt (macOS) and Landlock + seccomp (Linux) with dynamic workspace-based policies
  • Claude Code/Gemini CLI: Support sandboxing but ship with it disabled by default
  • OpenAI Codex CLI: Read-only, workspace-write, and danger-full-access modes

These tools use OS-level permission scoping rather than kernel boundaries, focusing on filesystem ACLs and network restrictions appropriate for the local development threat model.

Apple Containerization Framework

Apple's new Containerization framework (announced WWDC 2025) provides each container its own lightweight VM via the Virtualization framework on Apple Silicon:

  • Own kernel per container
  • Own ext4 filesystem
  • Own IP address
  • OCI image compatibility

This collapses the gap between "development containers" and "properly isolated sandboxes" in a way Docker Desktop never achieved.

Recommendations for Agentic Systems

Choosing the right isolation approach depends on your specific threat model, performance requirements, and compatibility needs. Here are guidelines based on different agentic AI use cases:

Local Development Agents (Cursor, Claude Code, OpenClaw)

  • Start with OS-level ACLs: Seatbelt/Landlock for filesystem and network restrictions
  • Upgrade path: Apple Containerization for stronger boundaries without VM overhead
  • Network strategy: Default network disabled, explicit approval for external requests
  • File access: Read/write workspace, read-only system areas, no write outside project

Multi-Tenant Code Execution (CI, Serverless, Agent Platforms)

  • gVisor: Good balance of compatibility, security, and performance
  • MicroVMs: When you need strongest isolation guarantees
  • WASM: For controlled execution where you control the toolchain
  • Network isolation: Stripped namespaces or proxy-based allowlisting

Crypto/Financial Agents

  • Hardware boundaries mandatory: MicroVMs for transaction signing and key management
  • Network isolation critical: Explicit destination allowlisting, no DNS resolution in sandbox
  • Formal verification: Where possible for critical decision logic
  • Audit trails: Complete logging of all agent decisions and actions

RL Training and Evaluation

  • Threat model: Both the generated code and potentially the worker nodes are untrusted
  • Bidirectional isolation: Protect host from agent and agent from compromised host
  • MicroVMs or gVisor: Depending on evaluation complexity and performance needs
  • Ephemeral environments: Clean slate for each evaluation to prevent state leakage

Decision Framework

Use Case Threat Model Recommended Approach Key Controls
Local Development Careless/confused agent OS ACLs (Seatbelt/Landlock) Filesystem restrictions, network approval
Multi-tenant Compute Adversarial escape gVisor or MicroVMs Kernel boundary, network isolation
Financial/Crypto High-value targets MicroVMs mandatory Hardware boundary, formal verification
RL Training Untrusted workers + code MicroVMs + defense-in-depth Bidirectional isolation, ephemeral state

Conclusions

Sandbox isolation for agentic AI systems requires understanding that different technologies provide qualitatively different security boundaries. The choice between namespaces, gVisor, microVMs, and WASM isn't about "stronger" or "weaker" isolation—it's about fundamentally different approaches to the isolation problem.

Key Takeaways

  1. Isolation is not binary: Understand the specific boundaries and failure modes of each approach rather than treating isolation as a checkbox.
  2. Network egress matters: Perfect compute isolation is meaningless without network controls. Exfiltration over HTTP bypasses all kernel-level protections.
  3. Threat model drives choice: Local development, multi-tenant hosting, and financial applications have different requirements and optimal solutions.
  4. Defense in depth: Layer multiple isolation techniques rather than relying on a single boundary. Each layer catches different attack classes.
  5. Performance trade-offs exist: Stronger isolation typically means higher overhead. Balance security needs against performance requirements.

The Agentic Security Challenge

Traditional sandbox isolation was designed for deterministic code execution. Agentic systems introduce non-deterministic decision-making that creates new security challenges:

  • Dynamic code generation requires runtime security decisions
  • Natural language instructions can be ambiguous or manipulated
  • Tool access management becomes critical when agents have powerful capabilities
  • Multi-agent coordination amplifies the blast radius of single compromises
Future Perspective: The transition from "Code is Law" to "Policy is Law" in agentic systems requires rethinking not just sandboxing, but the entire security model. We're moving from protecting against code vulnerabilities to ensuring agent behavior aligns with intended policies.

Market Opportunity

The gap between traditional isolation technologies and agentic security needs represents a significant market opportunity. Organizations building agentic systems need:

  • Agent-aware isolation platforms that understand AI-specific attack vectors
  • Policy enforcement frameworks that can verify agent behavior alignment
  • Dynamic security controls that adapt to runtime agent decisions
  • Audit and compliance tools for non-deterministic systems

The organizations that successfully bridge traditional sandboxing expertise with agentic AI understanding will define the security standards for the autonomous future.
